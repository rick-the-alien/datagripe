What each one costs

Editor tab

The table becomes a document. Opens beside your SQL, closes like a file.

  • Full width for wide tables
  • Two tables open at once, comparable
  • Costs zero permanent space
  • Hides your query while you look
  • Tab strip fills up fast

Inspector

Persistent right rail that follows tree selection.

  • Query and structure visible together
  • No explicit open or close
  • ~320px gone forever, even when unused
  • Too narrow for grants or DDL
  • Only ever one object

Bottom panel

A tab alongside results, in the space you already watch.

  • Editor stays visible above
  • Zero new chrome
  • Fights results for the same slot
  • Short and wide is wrong for 40 columns
  • Lost the moment you run a query

The overlap you flagged

Toggle fields into the tree and watch what happens: payments expanded pushes users, payouts and every other object below the fold, and the columns tab of the drilldown becomes a duplicate of what the tree is already showing. Two places to look for one fact, and the tree loses its job — navigating between objects — to do the drilldown's job badly at 11px in 216 pixels.

Keeping fields out buys back a level of indent, keeps sibling tables visible while you inspect one, and leaves each surface with one clear purpose. The cost is real though: no drag-a-column-into-the-editor, and no glance at a column name without opening something.

Middle path if that cost bites: keep fields out of the tree, but give table rows a hover peek — a small popover listing column names only, no types, no scrolling. Enough to answer "what was that column called" without rebuilding the level.

Empty and loading states

Your synthetic empty row is in the tree — expand sequences to see it. Worth noting the sibling case: a node that is expanded but still fetching looks identical to an empty one, so it needs its own row rather than nothing.
