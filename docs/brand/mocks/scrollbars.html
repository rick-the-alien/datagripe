Scrollbars

One rule, two places it matters: a tree that outgrows its pane, and a grid that scrolls both ways. Scroll both below.

The trick

The track stays 12px and the thumb wears a 4px transparent border with background-clip: padding-box. It reads as a 4px hairline at rest and thickens to 6px on hover, with no change in track width — so nothing reflows and the content never shifts sideways as you move the pointer over it.

Animating ::-webkit-scrollbar width directly is the obvious approach and it is wrong. The track is part of layout, so widening it on hover reflows the content underneath and the text you were reading jumps. The border trick moves only paint.

No accents. A scrollbar carries no meaning in this system, and the four accents are spoken for — a green thumb would read as a status.

The one place an accent belongs

Turn on annotation rail. Marks sit alongside the vertical scrollbar showing where the interesting rows are in the full set, not just the visible window — magenta for rows that failed a constraint, green for filter matches. This is the scrollbar earning an accent by carrying information the viewport cannot show.

Keep it sparse. A rail with two hundred marks is a gradient, not a map. Cap it — cluster nearby marks into one and stop drawing past roughly forty.

Sticky corners

The grid has a sticky header row and a sticky row-number column, so three things converge at the bottom-right: horizontal bar, vertical bar, and the corner between them. ::-webkit-scrollbar-corner fills with Panel — leave it transparent and you get a void-coloured notch that looks like a rendering bug.

The sticky row-number cell needs its own background at every row state, or content scrolls visibly underneath it. That is three extra rules and it is the thing most often missed.

Firefox and the rest

Chromium, Safari

Full control through the ::-webkit-scrollbar pseudo-elements. Everything above applies.

Firefox

scrollbar-width: thin and scrollbar-color only. Two colours, no hover thickening, no corner control. It degrades to a thin quiet bar, which is fine.

Both are specified, so the same class works everywhere and Firefox simply gets less. That is the whole compatibility story.

What not to do

Do not build JavaScript scrollbars. Restyled native overflow keeps momentum scrolling, trackpad behaviour, keyboard paging, screen reader semantics, and every platform convention for free. A custom implementation gives up all of it to gain a hover animation.

Do not auto-hide. A scrollbar that appears only while scrolling removes the single best signal that there is more content — which in a four-hundred-table tree is exactly the thing you need to know before you start hunting.

The CSS

:root{
  --sb-rest:#2A3448; --sb-hover:#3B4A66; --sb-active:#4C5D7E; --sb-track:transparent;
}

.dgs{                                    /* Firefox */
  scrollbar-width:thin;
  scrollbar-color:var(--sb-rest) var(--sb-track);
}

.dgs::-webkit-scrollbar{ width:12px; height:12px; background:transparent }
.dgs::-webkit-scrollbar-track{ background:var(--sb-track) }

.dgs::-webkit-scrollbar-thumb{
  background-color:var(--sb-rest);
  background-clip:padding-box;              /* border shows track through */
  border:4px solid transparent;             /* thumb paints 4px inside a 12px track */
  border-radius:8px;
  min-height:34px; min-width:34px;          /* grabbable at any content length */
}

.dgs:hover::-webkit-scrollbar-thumb{
  background-color:var(--sb-hover); border-width:3px;
}
.dgs::-webkit-scrollbar-thumb:active{
  background-color:var(--sb-active); border-width:3px;
}

.dgs::-webkit-scrollbar-corner{ background:var(--panel) }
.dgs::-webkit-scrollbar-button{ display:none }   /* no arrow buttons */

Apply .dgs to any scroll container: the tree, the results grid, the object view body, popover lists, the history table. It is one class and it is the only scrollbar styling in the product.
