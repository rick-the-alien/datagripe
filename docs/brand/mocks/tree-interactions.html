What the mock settles

Two openable surfaces, deliberately different weights. Table view is a double click and gets the whole pane — one filter line at the top, then rows all the way down. Object view is the ⊞ affordance or the context menu, and it owns everything structural. No data tab in it, as you specified; the two never compete for space.

Tab glyphs differ so the strip stays readable when you have both open for the same table: green ▤ for rows, cyan ⊞ for structure. Without that, two tabs both saying payments is a coin flip.

Danger zone

Last tab, pushed to the right edge behind a divider, dim magenta until hovered. Each action is collapsed until you click it, then asks you to type the object name. That's your extra click or two, and the typed name means muscle memory can't fire it.

Worth wiring to the project class: on an analytics read-only project the tab renders disabled with the reason, and on production the confirm could additionally require the project name rather than the table name. The colour class already knows — it may as well do a second job.

Open questions I hit while building

Single click on an already-selected table. Currently does nothing. Candidate: it could focus the field popover so keyboard users get the same lookup, since hover has no keyboard equivalent.

Multi-select scope. Ctrl click works on tables here. The context menu adapts, but it needs deciding what a multi-selection can actually do — export, generate a join skeleton, compare structures — before the menu grows a section that does nothing.

Popover while dragging. If you support drag-a-table-into-the-editor, the popover has to suppress on mousedown or it fights the drag.
